# API G04 — coordinación por proceso

`SingleFlight.run(key, async_factory)` en `analytics/infrastructure/singleflight.py`. No es caché ni lock distribuido. Se mantiene un estado separado por event loop del proceso (un loop habitual de ASGI); loops/procesos distintos no deduplican entre sí. No existe lock global con I/O bajo él: admisión/bookkeeping son pasos sin await. `stats()` expone entries/running/consumers del loop actual para contratos y pruebas, no un endpoint público.

## Dos niveles y claves

- **Respuesta:** `response_flights`, 20 endpoints por `cached_frame_endpoint` + `/gaze-at` JSON + `/heatmap` PNG = 22. `/participants` y `/scenarios` conservan SQL simple (sin cálculo/Parquet/caché de respuesta). Clave del helper: `(owner_id, Redis_key_completa, ParquetProjection_o_None, response_model)`; gaze añade su esquema; PNG usa `(owner_id, Redis_key_completa, "png")`. La clave Redis vigente conserva namespace/generación/proyecto/participante/endpoint/escenario y todos los parámetros, token de transformación, AOI digest, tamaño/duración/ventana/canales/procesamiento. El lector proyectado no se confunde con otro perfil. Auth/ownership de **cada solicitante** ocurre antes de los dos niveles; el helper confía en el Project ya autorizado que le entrega cada ruta.
- **Archivo:** `parquet_flights`, en `ParquetReaderService.read`: `(project_id, participant_code_exacto, ProjectFile.id, external_id, normalize_generation(generation))`. Identidad de archivo y configuración de almacenamiento/OAuth se resuelven secuencialmente en la DB del solicitante **antes de unirse**. El factory de descarga no accede a DB/ORM: sólo scalars/cliente/cache. Reconsulta `cache.get()` bajo coordinación y mantiene `put` atómico de archivo completo. Se comparte exclusivamente Path; cada `read` decodifica su DataFrame/attrs/índice/proyección propios. Full sigue default. Cache hit de disco conserva el acceso anterior sin DB/download.

Ambos niveles reconsultan la caché después de admisión y antes de producir. Hits de respuesta simples/persisted-token siguen sin construir lector/abrir Parquet. **Legacy sin token persistido conserva lectura previa y persistencia request-local**, antes de construir la clave; no se promete zero-read ni se deduplican esas lecturas/token-DB entre solicitantes. Informes/video que llaman `ParquetReaderService` reciben sólo coordinación de archivo; sus cálculos no pasan por el coordinador HTTP. G07/G08 siguen responsables de auth/DB/generación/concurrencia propia.

## Lifecycle y recursos

El primer consumidor es dueño de los recursos del factory de respuesta (lector/enrich que pueden usar su AsyncSession). El factory corre secuencialmente; el request dueño permanece suspendido en `run` hasta settlement, inclusive cancelación reiterada. **Cancelar el líder no permite que FastAPI cierre get_db** mientras un follower usa el cálculo; el líder espera shielded hasta que el factory termine y luego propaga CancelledError. El follower que cancela sale sin afectar supervivientes ni operar con su DB mientras espera. No se usa una AsyncSession desde tareas simultáneas: el request dueño sólo espera; el factory hace sus pasos DB uno por uno. Tests ejecutan ASGI/get_db real y AsyncSession subclass con transporte sintético, incluyendo SQL de enrich tras abort y durante DB await.

El último consumidor solicita cancelación; la entrada deja de aceptar consumidores hasta settlement. Un retry durante cancelación recibe Busy/503; después puede comenzar de nuevo. Errores se entregan a consumidores vivos; no se retienen como caché. Un timeout cancela después de 120 s desde admisión (incluye cola). Deadline **solicita** cancelación: el HTTP/error puede tardar más mientras termina I/O o CPU sincrónicos no preemptibles. `settled_thread` espera físicamente el worker bajo asyncio/AnyIO shield incluso cancelaciones repetidas; slots/entrada no se liberan por una cancelación meramente lógica. Transporte bloqueado prolonga su slot y lease DB; no se añade timeout de red ni se afirma latencia dura. El llamador debe esperar `run` dentro del lifecycle de sus recursos; no lanzarlo como tarea abandonada tras cerrar DB.

## Presupuestos e inmutabilidad

Cada nivel: **4 operaciones running**, **32 claves en cola** (36 entradas totales incluyendo settling), **256 consumidores activos**, deadline 120 s. Admisión falla antes de crear tareas adicionales; Busy/Timeout se mapean a 503 en HTTP. Se crean runners acotados por entrada; wait_for/settled_thread sólo tienen subtareas acotadas por operaciones admitidas. Cuando entradas/consumidores quedan vacíos se elimina estado del loop. Los slots son de operaciones, no un límite RSS; respuestas oversize/frames/HTTP en progreso aún usan memoria. Lecturas directas fuera de response_flights no tienen un nuevo límite de decodificaciones aquí; G07 debe aplicar su límite de I/O/frames. Se conserva el limiter de threads de AnyIO y sus configuraciones existentes.

JSON live: validación de esquema una vez en productor, `TypeAdapter(dict, config=ser_json_inf_nan="constants")` serializa el `model_dump()` Python a bytes inmutables; cada consumidor crea su modelo con `response_model.model_validate_json`. Mantiene float64 roundtrip, NaN/Infinity y metadatos anidados sin alias mutable. Esta configuración ya figura en [Pydantic 2.5](https://docs.pydantic.dev/2.5/api/config/#pydantic.config.ConfigDict.ser_json_inf_nan). HTTP/caché/keys no se versionan porque salida permanece equivalente. PNG comparte bytes inmutables; metadata se copia por respuesta y cada StreamingResponse/headers/iterador es propio. No se comparte DF.

Se conserva Redis best-effort/no Redis y su límite JSON existente de **8 MiB**: oversize se devuelve y comparte sólo live; no se convierte en una caché local persistente. Finalizado el trabajo se libera la entrada y un nuevo miss recalcula. No hay caché global de resultados científicos/eventos.
