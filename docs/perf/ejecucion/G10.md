# G10 — estadísticas de Comparativas

**Estado:** completa; pendiente de revisión del coordinador. **Base recibida:** HEAD `f310003` más G00–G09 y cambios locales preservados, con checkpoint G10 de 1.040 archivos protegidos y snapshot de alcance de 157 archivos. No se inició G11.

## Resultado

Comparativas obtiene gráficas y los resúmenes de sus cinco señales temporales en una respuesta versionada. Se eliminaron los cinco hooks `timeseries` que sólo alimentaban la tabla; peticiones legítimas de otros paneles (incluidos AOI y `gaze-at`) permanecen. Selección, orden, rótulos/unidades, pines, vacío y fallos parciales se conservan.

El backend calcula cada señal una sola vez y deriva el resumen desde las muestras/precisión equivalentes al endpoint histórico, no desde filas gráficas decimadas. El port conserva la reducción JavaScript en orden original y su tratamiento de finitos, par/impar, `n=0/1`, `n-1`, baseline, baseline cero, negativos, cancelación y overflow. Los resultados derivados no finitos viajan como `null`, que continúa mostrándose `—`.

Contrato completo y diferencias de resolución: [API.md](evidencia/g10/API.md). Versiones: payload `comparison-charts-v3`, estadísticas `comparison-statistics-v1`, Redis `comparison_charts:v3:statistics-v1:...` y loader G02 `getComparisonCharts:v3`. Auth por request, usuario/proyecto/generación/revisión/digest espacial, invalidación, singleflight G04 y límites del loader quedan intactos.

## Medición

Corpus golden sintético G00 `SYN-01/stimulus-a`, `max_points=5000`, mismo runtime Python 3.14.3/PyArrow 25, warmup 1 y n=5 ([resultado](evidencia/g10/benchmark-result.json), [probe](evidencia/g10/benchmark_g10.py), [validación de cierre](evidencia/g10/cierre-benchmark-verificacion.json)). Small usa batches de 10 por muestra; large reproduce la construcción G00 de 64 bloques/102.400 filas y usa una operación por muestra. No se repitió la medida en el cierre porque hashes, protocolo, resultado y construcción seguían vigentes.

| Corpus | Filas | Bytes JSON directos estimados, antes → final | CPU backend mediana n=5, antes → final |
|---|---:|---:|---:|
| small | 1.600 | 529.071 → 286.459 (-45,9%) | 87,50 → 82,81 ms (-5,4%) |
| large G00, 64 bloques | 102.400 | 3.379.386 → 1.832.079 (-45,8%) | 1.375,00 → 1.000,00 ms (-27,3%) |

Los bytes son la serialización UTF-8 compacta directa de objetos de servicio (`allow_nan=True`), no bytes HTTP reales, comprimidos ni transferidos. El CPU excluye red/Auth/Redis/Parquet; no se extrapola a latencia global. El probe anota 6→1 requests lógicos y 10→5 cálculos de servicio por la topología fija invocada; esos dos valores no son contadores dinámicamente instrumentados.

El contrato HTTP en proceso sí instrumentó llamadas: seis rutas frías anteriores frente a una final produjeron 6→1 invocaciones de `ParquetReaderService.read` y 2→1 de `transform_cache_token`. Esto comprueba la topología FastAPI del harness con almacenamiento detached/falso, no I/O Parquet cronometrado ni equivalencia con PostgreSQL o Redis reales. En navegador, la respuesta interceptada de cinco vistas tuvo 23.468 bytes de cuerpo decodificado y no agregó requests `timeseries` para los resúmenes; es un payload HTTP mock E2E, no comparable con las estimaciones directas del probe. No se verificaron Redis, Drive, PostgreSQL ni nube reales.
