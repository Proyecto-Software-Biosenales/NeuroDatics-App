# Student edition — M0 decisions and delivery plan

Status: **DISCOVERY — PREVIOUS PROPOSAL SUPERSEDED**, 2026-09-19.
M0 means T0 in the original sketch. Decisions and evidence: [LEDGER.md](LEDGER.md).

## Current owner direction — takes precedence over the previous proposal below

The application is a simple local viewer: no accounts, no backend verification
workflow; the user opens/uploads locally a project that has already been processed
and visualizes it. Signing, trusted issuers, approval workflows and scientific
export-certification gates from the initial proposal are withdrawn requirements.

Ask the important product questions before choosing the architecture or format:

1. What is opened: a teacher-exported file, a processed folder, or an existing format?
2. Does visualization mean the full interactive dashboard, saved results only, or a subset?
3. Must all use, including first launch after installation, work without internet?

Answered 2026-09-20 (see [LEDGER.md](LEDGER.md)): the student app is the current app
without accounts; visualization is the current functionality (full dashboard); delivery
is a package students download from Google Drive and run, with offline behavior to be
chosen from options. The opened artifact/format is still unresolved.

A local computation engine, persistence, media handling,
installer and package schema are implementation choices to derive from the answers,
not agreed requirements. No backend verification workflow does not by itself settle
whether existing analytics should run in a bundled local process or in the browser.

The earlier plan below is retained for reference only. Its proposed scope, task gates
and [package specification](PACKAGE_SPEC.md) are not the current approval target and
must be simplified after the product workflow is clarified.

## Objective

Deliver a Windows x64 student edition that a student can install and use without
Python, Node, Docker, an account, or an internet connection. The teacher prepares
a distributable project; the student imports it, selects participants and scenarios,
and explores the agreed dashboard with analytically equivalent results to the
teacher edition. Import, analysis, closing, and reopening all work offline.

M0's objective is narrower: agree on that user outcome, the screen/data/trust
boundaries, the interchange contract, the dependency order, and measurable release
gates. Record what has been demonstrated and what still needs an experiment.

## Roast session: what the sketch misses

| Finding | Consequence | Resolution in this draft |
| --- | --- | --- |
| Tasks name technologies before defining the student's lesson workflow. | A technically complete installer could still omit an essential classroom activity. | Scope below; owner must decide reports and media before the spec is frozen. |
| `READY` means a published ingestion, not a complete exportable project. | Missing or ambiguous participant files, media, or acquisition provenance can ship. | Add an export preflight and coherent metadata/file snapshot. |
| `ProjectCatalog` + `ParquetSource` leave dependencies behind. | Analytics still imports SQL/auth, constructs Redis, and writes PostgreSQL transform tokens on GET. | Also separate cache, media, token access, and composition. |
| Removing login does not remove authentication. | Shared API calls redirect without a session; comparisons call `useAuth()`. | Extract the dashboard body and transport policy; provide student preference scope. |
| Static build success does not prove offline behavior. | Google Fonts, Drive thumbnail fallbacks, Node rewrites, and login redirects remain. | Production static-server tests with non-loopback network blocked. |
| Pseudonymisation and literal response equality conflict. | IDs and labels legitimately change, but a broad normalizer could hide defects. | Explicit identity-field mapping; scientific values and provenance remain comparable. |
| Hashes do not establish who issued a package. | An attacker can replace both a payload and its hash. | Decide trusted signatures and key operations, separately from installer signing. |
| “Pure Python” and “no processing” are ambiguous. | Cryptography and numerical libraries have native dependencies; analytics still computes. | Container core has no app/storage dependencies; exclude ingestion, preserve analytics computation. |
| Testing packaging only after T5 is too late. | Native numerical dependencies and video tools could invalidate delivery assumptions. | Add an early frozen-runtime spike, then build the installer incrementally. |
| T5 and a clean-VM install test are both release gates. | Correct source-mode output says nothing about a broken executable. | Release requires equivalence, packaged integration, clean-VM use, and recorded performance. |

These are findings from the current working tree, not hypothetical redesign advice.
Evidence and source locations are in the ledger.

“Read-only” means imported scientific content is immutable. Local import, removal,
preferences, caches and schema upgrades may write locally. It does not mean GET-only
HTTP or that PSD/heatmaps are precomputed. Raw source ZIP/CSV files are excluded;
the processed numerical samples needed for interactive analytics remain included.

Windows x64 and a local browser are the proposed support boundary. Native is the
primary delivery candidate. A student Docker variant is deferred, not a second
mandatory product. The existing teacher Docker delivery remains separate.

## Architecture and ownership boundaries

Keep one implementation of analytical algorithms, shared read contracts and dashboard
features. Compose two applications around them. Avoid an `if student_mode` fork
through teacher routes/settings.

| Boundary | Contract | Teacher implementation | Student implementation |
| --- | --- | --- | --- |
| ProjectCatalog | Immutable read DTOs: project, participant ordering/mapping, scenarios, sensors, AOIs, placement, revision. | Existing SQL reads with existing ownership/validation semantics. | Separate SQLite schema and local package identities. |
| ParquetSource | Resolve participant data, preserving schema metadata and DataFrame attrs. | Existing SQL/Drive/cache resolution, including its guarded legacy fallback. | Explicit validated package file mapping; no filename guessing. |
| MediaSource | Resolve media, dimensions/type and preview inputs. | Existing storage behavior. | Package files; bundled preview tools if video is accepted. |
| AnalyticsCache | Current response/frame key semantics, bounded storage. | Existing Redis/disk behavior. | Memory cache with byte limit and eviction; immutable package revision in every key. |
| Transform token access | Lookup/derive/store through an explicit capability. | Preserve current PostgreSQL persistence and commits. | Package-derived/local token storage; no PostgreSQL import. |
| API/composition | Shared read services; separate dependencies and route assembly. | Existing auth and ownership gates. | Local catalog resolution, local settings, loopback server. |
| Frontend transport | Request/cancellation/error/blob behavior with injected auth policy. | Existing session/401 handling. | Same-origin requests without user auth; no teacher session imports. |

Proposed layout: `shared/package/` for the standalone container library;
`backend/src/neurodatics_student/` for the student composition/adapters;
`frontend-student/` for its static shell; `deployment/student/` for versioned build
sources; generated artifacts in `delivery/student/`. Existing shared analytics and
frontend features remain in their current trees unless a concrete extraction needs
a neutral home. T3 must prove neutral modules do not transitively import teacher
settings, ORM entities or entry points.

The student must not import teacher `main`, the aggregate router, auth, Drive,
PostgreSQL/Redis clients, project ingestion/use cases, or the mixed project router.
Use import-linter for source boundaries **and inspect the frozen bundle/module list**.
Excluding a route from OpenAPI does not exclude its dependencies from the build.

The local server binds to `127.0.0.1` only, owns API and static paths, and rejects
unexpected Host/Origin values. Import/removal require a same-origin request check
and a per-launch capability token; this is local request protection, not a login.
API errors must not fall through to the HTML fallback. Serve only validated media
IDs, never arbitrary paths. Store data under the user's local application-data
directory, outside the installed executable; bound memory, disk and import workers.

## Equivalence contract — define before implementation

T5 has two oracles:

1. Capture teacher responses for an approved, stable source fixture **before export**;
   compare student responses after real export, validation, import and local reads,
   applying only the documented identity/label mapping. This catches information
   lost by export as well as importer mistakes.
2. Run the same exported package content through teacher-side and student-side
   storage/catalog adapters. Use real Parquet bytes and SQLite; mock an external
   Drive boundary only where necessary. Do not mock the exporter, importer, DTO
   conversion, local catalog or analytics to make the gate pass.

Cover all 23 current analytics endpoints under `/api/projects/{project_id}/analytics`:
`participants`, `scenarios`, `correlations`, `comparison/charts`,
`timeseries/pupil`, `statistics/pupil`, `gaze-at`, `timeseries/gaze`,
`statistics/gaze`, `timeseries/distance`, `statistics/distance`,
`timeseries/gsr`, `statistics/gsr`, `timeseries/eeg`, `psd/eeg`,
`spectrogram/eeg`, `topography/eeg`, `scanpath`, `fixations`, `heatmap`,
`fixations/sensitivity`, `fixations/histogram`, `aois`.
Also cover project list/detail and included media read/preview contracts.
Verify route prefixes against the frozen baseline when implementing.

Project list/detail use the package's explicit privacy projection, not literal teacher
payload equality: map IDs/codes and reviewed labels; omit original demographics,
Drive/account/source-path fields, ingestion errors and original timestamps; include
only packaged file records. Where shared response types require a field, return an
explicit null or the documented package-derived value. Freeze this field-by-field
serializer map with the T3 DTOs and assert excluded fields cannot leak. Compare
sensors, participant/scenario relationships, AOIs and geometry exactly after mapping.
This exception does not weaken scientific endpoint comparisons.

- Exact: keys, types, shapes, ordering, null/missing positions, statuses, deterministic
  error details and scientific metadata/headers, after specifically listed identity rewrites.
- Numerical arrays/statistics: initially `atol=1e-8`, `rtol=1e-6`, matching the
  established numeric goldens. No tolerance expansion to hide export/refactor errors.
- Heatmap: numeric substrate, extent/geometry, decoded dimensions/alpha and metadata;
  deterministic decoded pixels on the same pinned runtime. Cross-platform rendering
  differences require a reviewed pixel criterion, not PNG-byte equality.
- Ignore only enumerated transport differences such as Date, timing, compression and
  opaque cache validators; test each implementation's conditional-request behavior separately.
- Matrix: at least two participants and scenarios; every supported sensor; missing
  samples/channels; absent optional media; transformed and supported legacy coordinates;
  each fixation threshold; bounded/full time windows; comparisons; cold/warm cache;
  ambiguous identity, incompatible provenance, unknown IDs and invalid parameters.
- Keep the existing synthetic goldens unchanged. Add package fixtures separately,
  including transformed geometry and video if accepted. Add an approved real classroom
  example when available; synthetic fixtures alone do not prove device diversity.

Record a Python/dependency profile for source and native runs. The current developer
environment is not a lockfile: its PyArrow version exceeds the declared range.
T5 runs on the chosen release profiles and again through the packaged student runtime.

## Release acceptance and performance proposal

Acceptance story: on clean supported Windows, a standard user installs the exact
artifact, disconnects external networking, imports the teacher's fixture, navigates
each included analysis/media workflow, closes and reopens the app, and retains the
library. Test paths with spaces/accents, occupied port, repeated launch, failed import,
update preserving data, and explicit data retention on uninstall.

Provisional performance envelope, to approve and measure: Windows x64 laptop with
4 logical CPU cores, 8 GB RAM and SSD; a declared fixture with 2–20 participants,
all three sensor families, 2–10 scenarios and at most 500 MiB compressed. Record row
counts, media bytes, CPU model, runtime versions and free disk. Candidate budgets:
launch-to-library <=15 s; import <=60 s excluding copying from removable storage;
warm ordinary dashboard requests p95 <=2 s; cold EEG/heatmap <=10 s; combined student
backend/browser working set <=2 GiB for that workload. These are proposals, not results
or claims about current performance. Report slow endpoints individually.

Record a cold run and at least 20 warm samples per declared interaction, including
peak memory, installed/package size, import failures and media seek. If comparing
Docker with native, run the **same student workload and algorithms on the same
machine**. Teacher-stack versus student-native numbers are contextual, not a causal
Docker-overhead comparison. Do not build a second student distribution just to fill
a benchmark table unless that decision is still open.
